Tags: PROVEN = I measured or ran it; DOC = a number from the repo docs; PROJECTED = my inference.
1) Native VP8 is never provisioned or enabled by any start script (grep: zero hits in scripts/*.sh and /workspace/run-musetalk-local-trt.sh). The live user server (pid 3555159, started via vast_onstart) runs with WEBRTC_VP8_ENCODER unset (pyav), MUSETALK_VAE_BACKEND=trt_stagewise int8_mixed and no motion atlas. That is the old recipe.
2) The only launcher for the fast path (TRT UNet + TAESD) is outside the repo: /workspace/experiments/chinese_bob_webrtc_20260927/run_local_api.sh. It skips run_trt_stagewise_server.sh, so the launcher's WebRTC defaults are never applied: edge-silence trimming falls back to ON (the API default), and the track crossfade falls back to 0 while /capabilities reports 2.
3) Native VP8 works on this box. PROVEN: `install_native_vp8.py --verify` passes; the configure_vp8_encoder startup probe passes at both default and 3.5M/2.5M bitrate settings; 22 CPU unit tests pass. It hard-requires Linux x86_64, CPython 3.10, glibc >= 2.17 and exactly aiortc 1.14.0, av 16.1.0 and cffi 2.1.1. cffi is not pinned by any setup script. It also needs a network download of the pinned aiortc 1.11.0 wheel, or `--wheel` for an offline install. Once opted in, it never falls back. Clients that offer only H264 get HTTP 400.
4) Encoder cost (DOC, from the 4070S evidence digest): native VP8 at 1 thread costs 4.0 ms/frame. aiortc libx264 costs 11.5–26 CPU-ms/frame. The api_server NVENC patch does nothing on aiortc 1.14, because h264.py:270 hardcodes libx264. prefer_h264 runs after setRemoteDescription, so in pyav mode the client's offer order decides the codec; the chinese_bob wall log shows libx264. Native VP8 uses 2 threads at 512x896, and there is no env setting to reduce that.
5) PROVEN bug: the registry directory the docs use, WEBRTC_MOTION_ATLAS_DIR=/workspace/experiments/realtime_characters, now raises "Multiple motion atlases match this character" for japanese_20260925 and latina_guided_20260925. The cause is the 2026-09-26 variant folders, which have the same source hashes and no motion-registration.json. Indian is fine. Session creation for the Japanese and Latina pose sets would therefore fail.
6) No motion atlas is reviewed; all are candidate_requires_recorded_review. Without WEBRTC_MOTION_ALLOW_UNREVIEWED=1, any matching bank raises an error. Atlases and registrations are not in the repo or in S3; S3 restores only avatar caches. A fresh machine therefore gets no matched-motion multipose (configured_bank returns None).
7) Kokoro is not installed by any setup path. The server setup passes --install-server-deps, and requirements.txt (which lists kokoro==0.9.4) is only used with --install-runtime-deps. The current venv has kokoro 0.9.4, misaki 0.9.4, espeakng_loader 0.2.4, spacy 3.8.16 and en_core_web_sm 3.8.0 only because of a manual uv install on 2026-09-27. The model (hexgrad/Kokoro-82M, 314 MB) and TAESD (madebyollin/taesd) sit only in /root/.cache/huggingface; models/ is gitignored and download_weights.sh fetches neither. espeak is bundled in the pip wheel, so no system espeak is needed. Kokoro loads lazily, in-process, on CPU. DOC: about 8.8 audio-seconds per second of throughput, and 30–85% CPU at 15 speakers.
8) System dependencies: ffmpeg and coturn (apt, setup_trt_stagewise_server_env.sh:82-99). libvpx, libx264 and opus come bundled in PyAV's av.libs, so there is no system libvpx dependency. mediapipe/FaceMesh is needed only offline, in other venvs; the chin alignment and refined seam are not in the live server at all.
9) WebRTC batch size snaps to the first list of MUSETALK_TRT_STAGEWISE_WARMUP_BATCHES, then HLS_SCHEDULER_FIXED_BATCH_SIZES (api_server.py:3803-3820). These must equal the UNet engine batches and MUSETALK_TAESD_WARMUP_BATCHES (8 today). The GPU-aware defaults produce [4], [4,8], [8,16] and so on, which do not match a bs8-only engine.
10) TURN: the relay-only coturn range is 49160–49200, which is 41 ports. PROJECTED: at roughly 3 allocations per session, that supports about 13 concurrent relay sessions, below the 15–20 stream target.
11) The multipose docs validated OMP/OPENBLAS/MKL at 4 threads, with MUSETALK_CPU_TUNING and OMP_PROC_BIND off. The CPU-tuning profile was rejected after 3.6 s returns.
12) No startup warmup exists for Kokoro, avatar caches or the pose lab. Health reflects only manager init; STARTUP_TIMEOUT_SECONDS is 600.

    The live user server (pid 3555159, launched via vast_onstart -> vast_server_ctl -> run_webrtc_relay_api_server.sh) runs the old recipe: MUSETALK_VAE_BACKEND=trt_stagewise, MUSETALK_TRT_STAGEWISE_PRECISION=int8_mixed, PROFILE=throughput_record, no WEBRTC_VP8_ENCODER, no WEBRTC_MOTION_ATLAS*, no OMP threads.
    The only TAESD launcher (experiments/.../run_local_api.sh) bypasses run_trt_stagewise_server.sh, so WEBRTC_TRIM_EDGE_SILENCE falls back to True (webrtc_audio_timeline.py:176) instead of the intended 0 (commit 763297d). WEBRTC_POSE_CROSSFADE_FRAMES falls back to 0 in webrtc_tracks.py:66 and hls_gpu_scheduler.py:233, while /capabilities reports 2 (api_server.py:1293).
    PROVEN (CPU run of configured_bank): the doc-recommended WEBRTC_MOTION_ATLAS_DIR=/workspace/experiments/realtime_characters raises ValueError 'Multiple motion atlases match this character' for japanese_20260925 and latina_guided_20260925. The 2026-09-26 variant dirs (japanese_fixedheight/onepass/onepass_r38/onepass_x38y22, latina_fixedheight/onepass/onepass_x38y22) carry atlases with identical source hashes and no motion-registration.json. Pose-set session creation for those characters would fail (webrtc_pose_router.py:221-222).
    Every atlas is status=candidate_requires_recorded_review. Without WEBRTC_MOTION_ALLOW_UNREVIEWED=1, a matching bank raises (motion_transitions.py:362-365), which fails the session rather than falling back.
    Character packages (motion-atlas.json, motion-registration.json, session-pose-set.json) are neither in the repo nor in S3; AVATAR_S3 restores only prepared caches. A fresh machine has no matched-motion bank and multipose silently degrades (configured_bank returns None).
    Kokoro is never installed by setup. setup_trt_stagewise_server_env.sh passes only --install-server-deps; requirements.txt (kokoro==0.9.4 at line 8) is only used with --install-runtime-deps, and would also pull tensorflow 2.12/gradio. KOKORO_SPANISH_MULTIPOSE_TEST_2026-09-25.md:36 records Kokoro missing from the venv; it is present now only through a manual uv install.
    No pre-cache for Kokoro-82M, Kokoro voices, spaCy en_core_web_sm or TAESD: download_weights.sh has no taesd/kokoro entries and models/ is gitignored. misaki/en.py:500-501 calls spacy.cli.download at runtime when the model is missing. With HF_HUB_OFFLINE=1 (as in run_local_api.sh) a fresh box would fail at first TTS or TAESD load.
    cffi is not pinned, but native VP8 demands cffi==2.1.1 exactly (webrtc_native_vp8.py:19,68-76), so a fresh resolve can hard-fail startup. scripts/install_webrtc_deps.sh (recommended in TURN_API_README.md:36) installs unpinned latest aiortc/av/aioice, which also breaks the native check (and aiortc 1.14 requires av<17).
    The NVENC patch is dead code on aiortc 1.14: api_server.py:273-325 patches create_encoder_context, but aiortc/codecs/h264.py:270 hardcodes libx264 (preset default, tune zerolatency). wall_api.log:4 logs 'encoder set to h264_nvenc' but :882 shows codec=libx264. Digest cost: 11.5–26 CPU-ms/frame, about 7.9 cores at 300 fps.
    prefer_h264 is applied after setRemoteDescription (api_server.py:4539-4545), but aiortc negotiates codecs inside setRemoteDescription (rtcpeerconnection.py:903-907). In pyav mode the client's offer order decides the codec, as the multipose audit doc also states.
    Native VP8 inherits aiortc number_of_threads: 2 threads at 512x896 (installed vpx.py:29-37). Digest [M]: 35–45% more CPU than 1 thread under concurrency. There is no env setting for this.
    coturn relay range is TURN_INTERNAL_RELAY_MIN/MAX_PORT=49160-49200, i.e. 41 ports (run_turnserver_tcp_relay.sh:112-114). The server uses 1 TCP TURN URL and clients get 2 URLs (udp + tcp), about 3 allocations per session. PROJECTED ceiling: about 13 concurrent relay sessions, below the 15–20 stream target.
    The pose-lab catalog needs the original source MP4s at the absolute paths recorded in each atlas (webrtc_pose_lab_catalog.py:57-59 -> file_hash), so it is not portable. Runtime sessions hash the prepared cache videos instead.
    No warmup at startup (api_server.py:1016-1133): Kokoro cold-loads its 313 MB model on the first /webrtc/tts/kokoro call under a global RLock, and avatar caches load lazily. Health reflects only manager init. vast_server_ctl.sh STARTUP_TIMEOUT_SECONDS=600 may be too short for a fresh TAESD max-autotune compile plus TRT builds on a new GPU (PROJECTED).
    The chin alignment and refined seam the user requires are offline-only. Live WebRTC applies TAESD but not chin (chinese_bob README:34; digest 'Chin path ... Not in the live server at all'). Startup scripts cannot make chin live without code work.
    Doc/code discrepancy: api_calls.md:56-68 says `run_trt_stagewise_server.sh --profile baseline` uses INT8 VAE + TRT UNet split8 and builds UNet if missing. Without a profile env, the launcher defaults are MUSETALK_UNET_BACKEND=eager, MUSETALK_TRT_UNET_ENABLED=0, MUSETALK_TRT_UNET_BUILD=0 and MUSETALK_TRT_STAGEWISE_PRECISION=fp16 (run_trt_stagewise_server.sh:136-155).
    Doc/code discrepancy: WEBRTC_REACT_NATIVE_README.md:135-139 recommends fps=10, playback_fps=15, batch_size=2. The batch is snapped to the warmed batch 8 (api_server.py:3803-3820), and the validated multipose runtime is 20/20. The wall defaults to 15 generated / 30 transport fps, which duplicates frames (digest: 1.5x encode cost).
    Doc/code discrepancy: KOKORO doc says Kokoro was removed from the venv, but it is now present (installed 2026-09-27). requirements.txt pins typer==0.9.4 and rich==13.4.2, while the venv has typer 0.27.2 and rich 15.0.0.
    Stale artifacts: aiortc-1.6.0-cp38-abi3-...whl is tracked at the repo root (commit 88e871e) with zero references anywhere. turnserver.conf is tracked with a hardcoded IP and committed credentials. run_turnserver.sh points at a missing /workspace/turnserver.conf and uses sudo.
    GPU waste (digest, inferred from code): exact-silence turns and WEBRTC_RAW_IDLE_POSE neutral frames still run UNet+TAESD and then discard the output (hls_gpu_scheduler.py ~1763-1782).
    Kokoro supports only language codes 'a' and 'b' (kokoro_tts.py:21); the Spanish test used English phonemization.
open_questions:
    Should native VP8 become the default for every client? H264-only offers get HTTP 400 in native mode, and the mobile app repo is absent, so no one has confirmed that React Native and iOS clients always offer VP8.
    On hosts where the native preflight fails (aarch64, non-3.10 Python, a different cffi), should the launcher silently set WEBRTC_VP8_ENCODER=pyav or fail the boot? The code deliberately never falls back once native is requested.
    Is a small code change acceptable to run native VP8 at 1 thread? Digest: -35–45% CPU. No env setting exists today.
    Where should character packages (atlas, registration, session-pose-set) ship for 'any machine': repo, S3 next to the avatar tarballs, or a separate bundle? And which of the 2026-09-26 variant atlases (fixedheight/onepass/r38/x38y22) is canonical, so a clean registry holds one atlas per character?
    Should WEBRTC_MOTION_ALLOW_UNREVIEWED=1 be the default, given that no bank has a recorded review and every matching bank otherwise fails session creation?
    Is Kokoro needed on production workers, or only for wall/pilot demos? At 15 speakers it would take 30–85% of CPU in-process.
    What transport fps should the default be: 20/20 as validated for multipose, or the wall's 15 generated / 30 transport?
    What concurrency and duty cycle should TURN relay-port sizing target? Is relay-only (WEBRTC_ICE_TRANSPORT_POLICY=relay) still desired on non-Vast hosts?
    Does OMP_NUM_THREADS=4 help or hurt at 15–20 concurrent streams? It was validated only with sequential single sessions.
    Is live chin alignment in scope for this rework? It is offline-only today and needs FaceMesh (mediapipe is not in the runtime venv), so start scripts alone cannot deliver it.
