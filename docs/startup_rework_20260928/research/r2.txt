summary:
  You get the TAESD decoder today by setting one runtime env var, MUSETALK_VAE_BACKEND=taesd. It is not an avatar-prep parameter, not a per-request API field and not stored in avatar packages. The '100% chin alignment + refined seam' is not in the live server at all. It exists only as an offline render stage in character_factory/h3_avatar_workflow (chin.py plus render_stage.py), and no env var, API field or start script can turn it on.

TAESD path: scripts/avatar_manager_parallel.py:183 calls trt_runtime.load_vae_trt_decoder. That function checks taesd_backend_requested() at scripts/trt_runtime.py:2021, which reads MUSETALK_VAE_BACKEND in {taesd,tiny,tiny_vae} (vae_fast_decoder.py:58, committed). It then returns vae_fast_decoder.load_taesd_decoder(), which loads diffusers AutoencoderTiny from models/taesd, falling back to the HF id madebyollin/taesd. The decoder is torch.compile'd (max-autotune, dynamic=False, one graph per batch size) and warmed only at MUSETALK_TAESD_WARMUP_BATCHES (default '8'). The native SD-VAE encoder is kept (musetalk/models/vae.py:135-143; set_decode_backend swaps decode only). TAESD decodes the same SD1.x latent space, so existing avatars do NOT need re-preparing. This is shown by the 20260925 and 20260922 A/Bs, which used the same caches.

The start chain can never produce TAESD today. scripts/select_unet_trt_profile.py:75 hard-writes MUSETALK_VAE_BACKEND=trt_stagewise (int8_mixed) into the profile env. run_trt_stagewise_server.sh:124-128 sources that file AFTER the caller's env, which clobbers any exported MUSETALK_VAE_BACKEND=taesd. Then :138 defaults to trt_stagewise, and :459 runs the INT8 calibration/modelopt precheck whatever backend is set. Confirmed: the live user server (PID 3555159, port 8000) runs MUSETALK_VAE_BACKEND=trt_stagewise / MUSETALK_TRT_STAGEWISE_PRECISION=int8_mixed.

Every TAESD run so far bypassed vast_onstart. They called api_server.py directly: experiments/chinese_bob_webrtc_20260927/run_local_api.sh, and batch_three_pose.py:186-194 (sources the sm89 env, then overrides MUSETALK_VAE_BACKEND=taesd, MUSETALK_UNET_BACKEND=trt, MUSETALK_TRT_FALLBACK=0, MUSETALK_TAESD_WARMUP_BATCHES=8, HF offline).

On a fresh machine the TAESD weights are missing. models/ is gitignored (.gitignore:11) and download_weights.sh does not fetch madebyollin/taesd. The docs call them 'vendored', but that is local only.

Chin alignment: it needs per-source FaceMesh landmarks (track_stage.py; mediapipe 0.10.9 exists only in /workspace/SoulX-FlashHead/.venv, because the TRT venv has protobuf 7.36.1 and no mediapipe). It also needs per-frame FaceMesh tracking of each generated face over a 512x896 shared-memory IPC (hardcoded), a one-frame look-ahead filter, and research cache.pt/masks.npz files. Production avatar dirs contain none of this: none of the 33 local avatars have landmarks. So putting chin into production would need new prep artifacts plus runtime code.

The masks are compatible: the API hardcodes parsing_mode='jaw', cheek width 90 and extra_margin 10 (api_server.py:1038-1041). Those are the same settings the chin prep uses (prepare_stage.py:87,95,115), and they get baked into masks at prep time.

Commit c284891 ('TAESD + chin alignment 100%') contains no TAESD or chin-alignment code. It adds opt-in cheek/jaw blend env flags, a prep-time fixed-face-height mode and WEBRTC_RAW_IDLE_POSE. TAESD came in 9b90b92; the chin module came in e803a63.

PROVEN on the 4070S: TAESD VAE decode is 6.83 ms at batch 8, vs 138.4 ms for SD-VAE. End to end: 209-241 fps model path. GPU-only sustained run: 260.1 fps (bs8, 200 s). Offline chin, refined seam: 168.8/163.4 fps (Japanese/Latina). Offline chin v1, pipelined: 184.9/193.4 fps. Diversity batch: 148-171 fps. All of these exclude TTS, encode and transport. Live WebRTC with chin has never been measured; the plan projects a ~174-203 fps structural cap on the live server even without chin.

open_questions:
    Should the reworked default ship chin alignment at all? It is offline-only and would need a runtime port: landmark prep artifacts, a FaceMesh worker process or venv, an extra frame of latency and a GIL/process split at 15 streams. The alternative is to ship TAESD + standard jaw90 compose now (proven 209-260 fps GPU path) and make chin a later phase.
    Do the madebyollin/taesd HF files hash-match the local models/taesd copy? The local config was re-saved by diffusers 0.30.2. Should the install script pin a revision and verify sha256 (7e5863.../8b947c...) or just use the HF files?
    When a TAESD compile fails, should the start script fall back to eager TAESD (MUSETALK_TAESD_COMPILE=0, ~12 ms bs8) rather than SD-VAE? This needs a startup preflight, because the current code cannot degrade gracefully.
    Which GPUs must be supported? The cu121 torch 2.5.1 stack lacks Blackwell sm_100/sm_120. TAESD needs no per-GPU artifact, but the TRT UNet and the (uncommitted) TRT TAESD engines do.
