summary:
  Serving code reads about 250 env names (full scan of api_server.py, the scripts/* modules named in the task, musetalk/**). Perf-relevant knobs, verified in code:
- Decoder. MUSETALK_VAE_BACKEND (trt_runtime.py:122, vae_fast_decoder.py:81) defaults to "" = PyTorch SD-VAE FP16, about 47 fps. The fast recipe is MUSETALK_VAE_BACKEND=taesd with MUSETALK_TAESD_BACKEND unset (compiled: torch.compile max-autotune, warmup batch 8). The live server (pid 3555159) still runs trt_stagewise int8_mixed. Its log line says "VAE decode backend active: tensorrt_stagewise_int8_mixed". The value comes from select_unet_trt_profile.py:75, which hard-codes MUSETALK_VAE_BACKEND=trt_stagewise into every generated .runtime/*.env. run_trt_stagewise_server.sh:127 then `source`s that file, which overwrites anything the caller exported.
- UNet. MUSETALK_UNET_BACKEND defaults to "" = eager PyTorch. Fast recipe: trt plus MUSETALK_TRT_UNET_PATHS=8:<engine>. The only engine is a static bs8 torch_tensorrt .ts: batch_range [8,8], sm89 / TRT 10.3, a symlink to tensorrt_unet_static_bs8_20260529. MultiTrtUnetBackend (trt_runtime.py:1733-1746) accepts only batches that equal 8 or are multiples of 8. So batch buckets must be multiples of 8. The code's VRAM auto-defaults (concurrent_gpu_manager.py:115-150) give [4,8] on cards under 20 GB and [4] when PROFILE=baseline, and a padded batch of 4 would raise at runtime. Today only the profile env file prevents this.
- PROVEN (measured, offline, 4070S, bs8, TRT UNet + compiled TAESD): 260.1 fps sustained for 200 s (bench_gpu_path_baseline_trtbs8_taesd_200s.json). Also 209-241 fps end-to-end (component analysis doc) and 250.8 pipelined / 184.9-193.4 with chin100 (experiments/chin_fps_validation README). Turning the syncs off measured 258.1 fps, so no offline gain.
- Live multi-stream capacity with TAESD has never been cleanly measured. The single-process ceiling of about 174-203 fps is PROJECTED.
- 100% chin alignment has no code in the serving path at all: no CHIN symbols in api_server.py, hls_gpu_scheduler.py or api_avatar.py. It exists only in the offline harness in /workspace/experiments, which uses the SoulX venv's mediapipe. Every MUSETALK_CHIN_* knob in the 300 fps plan is a proposal that is not in the code.
- Uncommitted work-in-progress from another session: MUSETALK_TAESD_BACKEND=trt (with the TAESD_TRT_* flags), MUSETALK_TRT_UNET_CUDAGRAPHS, MUSETALK_UNET_BACKEND=trt_stagewise (with the UNET_STAGEWISE_* flags) and MUSETALK_FREE_EAGER_UNET. Their engines are not built (models/taesd/trt and models/tensorrt_unet_stagewise_sm89 are missing), and their gate runs are blocked by the live server holding 9.5 GB. None of them can be a default yet.
- Code defaults that differ from the live / fast values:
  - HLS_PREP/COMPOSE/ENCODE_WORKERS: code 2, live 8. Compose and encode are really max(6, n, min(10, nproc//2)), which is 10 here.
  - HLS_MAX_PENDING_JOBS: code 16, live 24. This is an admission cap, so a 15-20 stream target needs 24 or more.
  - HLS_SCHEDULER_STARTUP_SLICE_SIZE: code 2 (auto gives min(4, max)), live 8.
  - MUSETALK_TRT_FALLBACK: code 1, live 0. It governs the fallback for UNet, TRT-VAE and TAESD together. With 1, a TAESD failure silently drops to SD-VAE.
  - WEBRTC_TRIM_EDGE_SILENCE: code True, live 0.
  - WEBRTC_POSE_CROSSFADE_FRAMES: code 0 in hls_gpu_scheduler.py:233 and webrtc_tracks.py:66, but api_server.py:1293 advertises 2.
  - WEBRTC_VP8_ENCODER: code pyav, live pyav, the plan wants native.
  - PROFILE: api_server.py:617 and run_trt_stagewise_server.sh default to baseline; vast_onstart.sh and vast_server_ctl.sh default to throughput_record.
- Dead knobs:
  - The WEBRTC_H264_ENCODER/FRAMERATE/STRICT NVENC patch does nothing, because aiortc 1.14's H264Encoder._encode_frame always uses libx264. Only WEBRTC_H264_MAXBITRATE (h264.MAX_BITRATE) and the encode-timing wrapper still take effect.
  - WEBRTC_AUDIO_PREBUFFER_SECONDS and HLS_PERSISTENT_SEGMENTER are not read by any .py file.
  - HLS_SCHEDULER_AGGRESSIVE_FILL_MAX_ACTIVE_JOBS is only logged, never used.
  - All MUSETALK_TRT_STAGEWISE_* knobs are ignored once VAE_BACKEND=taesd.
  - The launcher-only knobs (MUSETALK_TRT_UNET_BUILD/_OUTPUT_DIR/_CAPTURE_DIR/_VALIDATE_* and the profile/restore knobs) are read only by shell scripts.
- MUSETALK_TRT_STAGEWISE_WARMUP_BATCHES is still read under TAESD, because api_server.py:3806 uses it to round WebRTC batch sizes. It must equal HLS_SCHEDULER_FIXED_BATCH_SIZES and MUSETALK_TAESD_WARMUP_BATCHES. Compiled TAESD uses dynamic=False, so any batch size not warmed up compiles lazily on the scheduler thread.

    The start scripts boot the OLD recipe. select_unet_trt_profile.py:75 hard-codes MUSETALK_VAE_BACKEND=trt_stagewise and MUSETALK_TRT_STAGEWISE_PRECISION=int8_mixed into every generated profile. run_trt_stagewise_server.sh:124-128 `source`s that file with set -a, so it OVERWRITES any MUSETALK_VAE_BACKEND=taesd the caller exported. Without a profile file a fresh box would run eager UNet + int8 SD-VAE stagewise (and needs the int8 calibration cache because REQUIRE_CALIBRATION_CACHE=1).
    Batch-bucket hazard. The auto-defaults (concurrent_gpu_manager.py:125-150) yield buckets containing 4 for PROFILE=baseline and on cards under 20 GB, 30-45 GB, or 45 GB and up. The only TRT UNet engine is static bs8 (meta batch_range [8,8]). MultiTrtUnetBackend._backend_for_batch (trt_runtime.py:1733-1746) raises 'engine batch support mismatch' for a padded batch of 4. Nothing validates the fixed buckets against the loaded engine at startup.
